# E02a process helper

`scripts/server_process.py` provides `ServerProcess` and sanitized
`ServerProcessError` exceptions using the Python standard library. It does not
read dotenv files, contact AWS, allocate S3 namespaces, or remove fixtures.

```python
from acceptance_support import load_config
from server_process import ServerProcess

config = load_config()
namespace = config.allocate_prefix(2, "types-crud")
server = ServerProcess(config, namespace, log_path="local-server.log")
with server:
    api_url = server.api_url
    token = server.private_token  # Pass privately to the ORM; never log it.
with server:  # Same namespace, token, and loopback port.
    pass
```

Call `start()` and `stop()` directly when a scenario needs an explicit restart.
`start()` returns the helper after `/health/ready` responds with status 200.
`stop()` sends SIGTERM and waits for the actual child exit, returning its exit
code. It is safe to call repeatedly. `pid` and `returncode` allow scenarios to
assert process outcomes. A running child rejects a second `start()`.

The default binary is `server/target/debug/meshdb-server`. Override it with
`binary=Path(...)`. Launch uses `Popen` without a shell and passes `serve`, host
`127.0.0.1`, an ephemeral port, four workers, and queue size 64. The helper selects
a free port locally and retains it across restarts. Releasing that reservation
before the server binds leaves a small port allocation race; a collision fails
startup and requires a new helper.

`startup_timeout=30` and `shutdown_timeout=10` are positive finite seconds.
Readiness requests have short socket timeouts and repeat within the startup
deadline. Startup failure and context exit stop and reap the child and close the
helper's log handle. If SIGTERM exceeds the shutdown deadline, the helper kills
the child and waits again with the same timeout. A forced kill raises an error
after reaping, so it cannot count as graceful shutdown. Failure to observe exit
after that second wait also raises an error; callers can retry `stop()`.

The child receives only `config.server_env(namespace)`. Ambient AWS settings and
MESHDB bucket/prefix overrides are not merged. The config's bucket and namespace
prefix remain authoritative; the supplied real configuration uses
`meshdb-testing`. Credentials and the token stay in the child environment, outside
command arguments and helper representations. Errors contain fixed diagnostics,
never child logs or environment contents.

`log_path` appends child stdout and stderr to a caller-selected local artifact.
New artifacts use mode 0600; callers control permissions of existing files.
Without a path, the helper uses a private temporary file and discards it on stop.
Treat retained artifacts as private because server output may contain secrets.

For native HTTPS pass all of `tls_cert=Path(...)`, `tls_key=Path(...)`, and
`test_ca=Path(...)`. Incomplete inputs, unreadable material, and mismatched
certificate/key pairs fail locally before launching. Encrypted keys requiring a
password are unsupported. Readiness uses a verified SSL context trusting the
test CA, with hostname checking enabled for `127.0.0.1`. The certificate therefore
needs an IP SAN for that address. Redirects and ambient HTTP proxies are not used.
E02a does not generate TLS material.

# Verification

Ran from the repository root on 2026-11-10:

```sh
PYTHONDONTWRITEBYTECODE=1 /usr/local/bin/python3.12 -m unittest discover -s scripts -p test_server_process.py -v
PYTHONDONTWRITEBYTECODE=1 /usr/local/bin/python3.12 -m unittest discover -s scripts -p test_acceptance_support.py -v
```

Both focused guards passed, one test each. The lifecycle guard launches an actual
tiny Python HTTP subprocess with synthetic config. It checks readiness, default
launch arguments, isolated environment, start/stop/restart with the same namespace
and token, exit on SIGTERM, cleanup after a scenario exception, cleanup after a
readiness timeout, and rejection of incomplete TLS inputs. It does not read the
repository `.env` or call AWS.

The Rust binary is unavailable. Real Rust startup, catalog readiness, work
draining, S3 persistence across restart, forced shutdown, and a verified HTTPS
handshake remain unverified. E02 must build and exercise the actual server. E03
must supply matching TLS material and test the native HTTPS path. No Rust
integration success is claimed here.
