## Checked scope in the prepared scenario

The main table `concurrent_rows` starts with one row. Four ThreadPoolExecutor
workers each construct a separate public DB, transport and discovered Table.
A 20-second Barrier coordinates their start. Each inserts five disjoint rows
in one insert_many request, with a 30-second transport timeout. Exact sorted
rows, projected keys and count must match all 21 expected records. Workers are
joined on success, failure and Ctrl-C before the process stops. Worker errors
fail the scenario; no request is retried. Unknown outcomes abort without replay.

A separate populated `replaceable_rows` table supplies the old handle and query.
After drop and recreation under the same name, the new ID must differ and the
old handle must retain its ID. Old get, query.collect and update must each
return exactly NotFoundError/not_found/404/not_applied. The recreated table
uses the same row key with a different value and must retain that value. Both
live tables remain populated, with 21 and 1 rows. The dropped table's objects
remain untouched.

The read-only S3 reader captures a baseline catalog and listing while both
original tables are populated. After concurrency and replacement, it validates
catalog format_version 1, a later integer revision, exact live names/IDs/counts,
and canonical relative references present in the final listing. Every baseline
snapshot must remain listed with its original size. The main populated baseline
must be historical, the dropped populated snapshot must remain in its old ID
directory, and the main ID directory must contain at least six revisions.

Two current snapshots, the populated historical main snapshot, and the populated
dropped snapshot receive only first-four-byte and last-eight-byte reads. Both
ends must contain PAR1; the little-endian footer length must be positive and fit
within the listed object size. This checks framing, not complete Parquet contents.
Rows and scalar types in this fixture are checked through the real server/ORM.
No Parquet package is imported.

The only CLI command shapes are:

```text
aws s3api list-objects-v2 --bucket meshdb-testing --region us-east-1 --prefix <exact-allocated-prefix> --max-keys 100 --no-paginate --output json --cli-connect-timeout 5 --cli-read-timeout 10
aws s3api get-object --bucket meshdb-testing --region us-east-1 --key <namespace.key(validated-relative-key)> --range bytes=<bounded-range> --output json --cli-connect-timeout 5 --cli-read-timeout 10 <private-local-file>
```

The executable is `/usr/local/bin/aws` when present, otherwise `shutil.which`.
Each command checks config._check_namespace and the fixed bucket/region; each
listed/addressed key passes namespace.key. Snapshot paths must match canonical
`tables/<uuid>/<uuid>.parquet`. Listings reject truncation and more than 100
objects. The catalog range is bytes=0-1048576, at most 1 MiB plus one byte, and
catalog overflow is rejected. Snapshot ranges contain only 4 or 8 bytes.
Subprocesses use arglists, private config._aws_env(), stdin/stderr DEVNULL,
privately parsed stdout, no shell, and a 20-second wall timeout. No ambient AWS
overrides, preflight, identity lookup, bucket management, other services,
remote deletion or general command dispatcher is used. Caller-owned local
files are private and removed after each read; the temporary directory is
removed after process shutdown.

## Report contract

Root fields are version, status, cancelled, scenarios, and optional sanitized
setup failure. The one scenario reports fixed safe bucket/region, allocated_prefix,
fixture IDs/names/latest checked counts/state, check labels/status/allowlisted
failure types, concurrency parameters, elapsed_seconds, status and cancelled.
`storage` is null until final inspection begins; thereafter it contains
catalog_revision, object_count including catalog.json, current_reference_count,
historical_count excluding current references and catalog.json, and
inspected_snapshots. Each inspected entry has relative_key, size_bytes,
first_magic, last_magic and footer_length_sane. Partial inspection results remain
in failure reports. No rows, raw catalog, tokens, environment, credentials,
private certificates, server logs or exception messages are serialized.

SIGINT during worker work cancels future work and waits for submitted workers.
Cleanup defers SIGINT while the server stops and local files are removed.
Cancellation saves a partial failed report and returns 130. Forced/nonzero
server shutdown also fails acceptance. No mutations or S3 objects are replayed
or deleted after any failure.
