# DN-A19 managed provisioning foundation

Adopted design handoff, 2026-11-11, after independent reconciliation found no essential correction. Refine C05 into four sequential Sol-high minis. The extra first mini is necessary because Rust has no A04 callback command/reply codec or immutable command handoff. Deliver only start allocation, start delivery metadata and bounded inventory reconciliation. Real dispatch, authorization, runtime supervision, C06 drainage/termination and C07 autoscaling remain later work. This note establishes no implementation, compilation or test guarantee.

## Sources and actual boundaries

[Shared contracts](../../plans/distributed-contracts.md) and the [rubric](../../plans/distributed-nodes.md) govern. Apply accepted [A05](DN-A05.md), [A08](DN-A08.md), [A10](DN-A10.md), [A11](DN-A11.md), [A14](DN-A14.md), [A16](DN-A16.md), historical [A03](../../scripts/notes/DN-A03.md), and [A04](../../orm/notes/DN-A04.md) including its accepted completed-cache removal override. Do not adopt A03's superseded deadlines, compaction, split storage or zero-minimum autoscale proposals.

Actual `member.rs` exposes `Node`, `Intent`, `Delivery` and their fields, with strict bounded `decode/encode/validate`. `state.rs` exposes `Control`, generation-2 `Config`, `capacity()` and `check_new_admission()`. Capacity derives first-stop credits from exact retained starts/stops and terminal witnesses. Decoding validates structure, not the history or truth of those witnesses. No schema or public SDK amendment is needed here.

`configuration::{Template,Timing}` already validates timings and fingerprints the exact outgoing Template. `configuration::bounded` is the reusable bounded writer. `store::LoadedControl::root()` exposes an immutable root; its token stays private. `PreparedOwnership::submit` already consumes one Match and performs at most one reconciliation read, returning `OwnershipOutcome::{Acknowledged,ObservedExact,Conflict,Unknown}`. Do not call its ownership-only constructor with a lifecycle change.

`controller::{Owner,OwnershipObservation,OwnershipGuard}` provides exact owner/epoch values, complete encoded-root observation and final generation/root/time authorization. These are metadata and local certainty boundaries, not provider fencing. `attachment::AttachedConfig` currently has private `loaded` and `local` fields and no accessors. `local: ApiReady` retains `prepared.auth.enrollment_token`, validated local material and the constructed HTTP client. No other module can currently retrieve enrollment through AttachedConfig. C08b2c S3 composition remains pending.

C03a has specification and quality PASS per the parent. Actual `membership::{registration_plan,ready_candidate,loss_candidate}` returns an exact existing binding or non-Clone `MembershipCandidate`. Its consuming `pub(super) into_parts` returns captured `OwnershipObservation`, `Owner`, and resulting `Control`. It is pure metadata. [DN-C03a](DN-C03a.md) records its evidence limits. C03b's common Match extraction and membership submission, and C03c/d heartbeat writers/observations, are specified in A16 and are not implemented. No mini may silently assume them. No unfinished R03a3a sequence source was inspected or is required.

Python `_callback_protocol.py` retains exact command bytes, validates start/stop/inventory shapes, bounds bodies to 1 MiB and depth to 32, and validates result strings/null/complete inventory. Inventory allows at most 4096 records and rejects duplicate resources and duplicate active node/request identities. Its authorization client compares the SHA256 of original bytes. A04 defines correlated success/error envelopes and HTTP status/code pairs. `_callback_pool.py` distinguishes pre-entry `not_invoked` from entered/uncertain `unknown`; neither Python completion nor callback transport alone commits Rust metadata. Completed Python results have no cache.

## Common candidate and accounting rules

All proposed cross-module interfaces below are `pub(crate)` unless narrower visibility is stated. Fields and constructors stay private; diagnostics show fixed categories only. Use existing `StorageError` classifications. A malformed root is `InvalidCatalog`, an ineligible owner/phase/binding is `Conflict`, and checked exhaustion is `LimitExceeded`.

Every mutation validates the complete base through `OwnershipObservation::new`, requires held exact `Owner { process_id, epoch }`, rejects the base proposal UUID, checks root revision + 1, and validates/bounded-encodes the complete result. Fresh UUID generation belongs to the later caller. Validate proposed node/launch IDs against every retained identity role, including current/retired incarnations, sessions, drains, deliveries, nodes and intents; never reuse or prune retained identities. There is no way to validate historical proposal UUIDs that the fixed root no longer stores; retain A10's caller freshness obligation rather than add a ledger.

Preserve config, Template, Timing, controller, policy including its independent revision, admin head/sequence and unrelated records exactly. Allocation and successful recovery preserve scheduler fields. Failure candidates may change only the documented scheduler failure/backoff fields and their one intent. Never reset persisted attempts, retry_at_ms, scheduler failures/backoff or degradation merely because authority, policy or process changes. Preserve cooldown and low_since here; C07 owns their policy meaning.

`managed_capacity(root) -> Result<u64, StorageError>` counts the union by retained node/launch, once each. A launch consumes capacity unless an irreversible exact terminal witness proves no resource can still appear: a failed start with `not_invoked` or `terminated`, or a matching completed/failed stop with `terminated`. All other starts, including pending, in_progress, reconciling, completed/resource_known, unregistered, overdue, draining, lost and stale members consume capacity. Node phase alone never releases it. A known positive resource belongs to that same launch, not an additional count. Unknown/conflicting inventory blocks allocation until reconciliation; it cannot be guessed into this union.

Allocate at most one fresh node/start pair when managed mode has a deficit against persisted desired, scheduler backoff permits it, and the complete candidate passes `check_new_admission()`. Node starts unregistered/starting with null resource/incarnation/endpoint/session/drain, empty retirements and stored Template capacities. Intent has request_id = launch_id, action start, pending, attempts 0, null delivery/resource/incarnation/error/outcome, stored template fingerprint, created/retry time = now and checked deadline = now + readiness_ms. Insert both arrays in sorted order. Its new first-stop credit is part of the same candidate. No separate start for an existing node.

Projected public-status admission remains an additional real gate before allocations are enabled. It must encode the existing complete public response envelope under 1 MiB with the later status owner. A boolean supplied by a caller implements neither that gate nor inventory/drain authority. Pure candidate construction and Fake submission tests below do not enable production allocation. Retained recovery and A08 reserved first-stop conversion must remain possible even if status cannot fit.

## 1. C05a, fixed Rust callback codec and retained command material

Own new `server/src/cluster/callback.rs` and private `callback/tests.rs`; only the narrow accessor below and its tests in `attachment.rs` / `attachment/tests.rs` are additional ownership. Parent owns the module declaration. No listeners, startup IPC codec, Python edits, storage writes or provider calls.

Add `AttachedConfig::callback_enrollment(&self, current: &Control) -> Result<&str, StartupError>` with cluster-parent visibility. Compare current cluster/name/config/provisioning/Template/Timing to the retained attached root's immutable values, validate the current root, and borrow `local.prepared.auth.enrollment_token`. Policy/controller/member progress may differ. Return no raw material bundle or backend token. Do not widen AttachedConfig's fields, reopen files, or substitute local Template paths. Existing Auth/ApiReady fields already provide the retained bytes, so no files.rs accessor is necessary.

Concrete private records are `StartCommand`, `InventoryCommand`, `ReplyContext`, `CallbackReply`, `InventoryRecord` and `InventoryEvidence`. `StartCommand::build(root, owner, intent_id, invocation_id, &AttachedConfig)` reconstructs the exact A04 start envelope and complete A03 payload from the retained intent and stored Template, validates every identity/capacity/field and only then serializes once and hashes exact bytes. Start bootstrap has advertise_url null. Enrollment exists only in memory; command bytes are never Serialize input to Control. Keep the immutable bytes and digest together, non-Clone, with value-free Debug. Inventory build has null intent/target and empty payload; it creates no durable intent. Stop wire decoding may validate its fixed resource/target shape for parity, but there is no stop builder or eligibility grant in this mini.

Expose fixed operations `validate_start_bytes(raw, root, &AttachedConfig)` and `decode_reply(status, raw, &ReplyContext)`. The former strictly decodes original bytes, reconstructs expected semantic payload from persistence and retained enrollment, compares it completely, then hashes the original bytes. It must not authorize a hash alone or require cross-language canonical bytes. The latter rejects duplicates, missing/unknown fields, noncanonical UUIDs, bad exact numeric types, depth/body overflow, wrong invocation/action result and invalid status/code/outcome pairs. Use strict object visitors and the existing bounded writer, not an unbounded Value parse or a new serializer framework. A04 success has `{version,invocation_id,result}`; failure has `{version,invocation_id,error:{code,outcome}}`. Uncorrelated pre-parse errors can only become unknown delivery evidence. Resource strings follow existing UTF-8/control/256-byte rules. Only a complete valid inventory success constructs opaque InventoryEvidence, retaining command owner/epoch, invocation and the admitted complete-root observation. These associations are local assertions, not authenticated provider certificates.

Focused private tests use literal Python-compatible A04 vectors, real Control/Template codecs and synthetic retained Auth/material. Independently fixed exact-byte hashes must include the enrollment bytes without printing them. Relocate local material, attach with identical identities, delete the synthetic files, and reconstruct using original persisted path hints. Change only invocation, owner, enrollment or payload to establish distinct rejection/hash causes. Cover start string, stop null and valid inventory positive controls; independently corrupt reply correlation, result type, status/outcome and duplicate active inventory bindings. Reuse existing strict parser tests for generic rejection coverage instead of copying a CRUD/JSON matrix. No Python/network execution is required here.

Only provision and its children construct it; consuming `pub(super) into_parts(self)` exposes exactly those three parts for the store child. There is no arbitrary Control/bytes constructor. This same finite candidate is used by minis 3/4.

No generic transaction closure, second outcome framework, history lookup or token accessor. At most one Match and one reconciliation GET under the original absolute deadline. ObservedExact requires the whole exact candidate and UUID; a later root cannot prove an earlier proposal occurred. Unknown, cancellation and timeout never imply rollback or authorize a fresh identity.

Check one atomic allocation, its extra credit, sorted arrays, desired zero/no deficit, ID collisions, revision/deadline overflow and saturated augmented admission. Assert one PUT/one reconciliation and preserved policy/admin/controller/config fields. Projected status is still an enabling prerequisite, not a claimed test result.

## 3. C05c, start claim and exact delivery outcomes

Depends on C05a/b. Own only new `server/src/cluster/provision/delivery.rs` and private `delivery/tests.rs`; provision.rs ownership is limited to its child declaration and narrow reexports. No controller/store algorithm changes. Implement `claim_start(root, owner, intent_id, invocation_id, &AttachedConfig, now_ms, proposal) -> Result<StartClaim, StorageError>` for an undispatched pending start only. Retries require mini 4. Respect retry_at_ms and scheduler.backoff_until_ms, checked attempts + 1 and max_attempts. Completed/failed/known-resource/terminal launches refuse entry. Draining launches do not get a new start callback.

Parent sequencing clarification after C05b review: C05c additionally owns only the start-delivery portion of A21's adopted private ReplyContext association in `callback.rs` and its focused tests. Retain the validated start target and exact command digest when constructing the context; provide the narrow read-only intent identity and `matches_delivery(root, owner, intent_id)` needed by completion. Validate the current exact start delivery without requiring the pre-claim context's observation to equal the claimed root. Keep fields private and preserve wire decoding, original bytes, inventory behavior and redaction. This moves the existing A21 prerequisite forward; stop construction and common start/stop extraction remain C06c. Existing attachment fixtures are available through their cluster-scoped test visibility; no duplicated module inclusion or material accessors are needed.

StartClaim privately owns the ProvisionCandidate and exact StartCommand. Candidate sets in_progress, increments attempts and stores only `Delivery { invocation_id, owner_id, epoch, command_sha256 }`, preserving immutable launch/template and retry history. Consuming `into_parts` yields candidate plus opaque `PendingStart`. PendingStart retains the complete expected claim root and command. `confirm(self, &OwnershipOutcome)` yields `ConfirmedStart` only for Acknowledged or ObservedExact of that whole root. Conflict/Unknown release no command for dispatch. Confirmation is metadata evidence only; later final authority and Python's fresh callback-entry authorization are mandatory. ConfirmedStart consumes once into exact bytes plus ReplyContext for one HTTP attempt. Neither command reconstruction nor confirmation is a reusable authorization ticket.

Implement `complete_start(root, owner, &ReplyContext, reply: CallbackReply, now_ms, proposal)` and `uncertain_start(root, owner, &ReplyContext, now_ms, proposal)`, returning ProvisionCandidate. Require current held owner and exact still-current delivery tuple, digest, action and launch. Stale callback replies cannot complete a new owner's claim. Valid positive resource success binds both Node and start resource and completes resource_known without changing registration/state/readiness/drain. Reject resource collisions and terminal contradictions. Late evidence from an obsolete delivery must be independently recovered through exact inventory under the current owner.

Transport loss, malformed replies, timeout, uncertain entry and unknown errors move the same start to reconciling with last delivery and attempts intact. Checked failure updates set a fixed sanitized intent error, retry_at_ms, scheduler.failures + 1 and scheduler.backoff_until_ms. For positive counter k use delay(k) = min(retry_max_ms, retry_initial_ms * 2^(k-1)), computed by at most 64 bounded doublings without overflowing an intermediate product. Use attempts for intent delay and the incremented scheduler failure count for global delay, with checked timestamp addition. Choosing the configured cap is intentional bounding, never arithmetic saturation. Keep existing later retry/backoff deadlines if greater. No success resets global failure history in this foundation.

The only failed/not_invoked terminalization supported here is a correlated definite pre-entry reply for the first claimed attempt, with attempts = 1, state still in_progress, exact initial delivery current, no registered boot and no known resource. Exclude identity_conflict and callback_in_progress from this proof; those imply potentially competing active work. A previously reconciling attempt cannot take this shortcut. Persist the accepted evidence as failed/not_invoked in the same candidate, leaving node identities retained. Every later-attempt pre-entry rejection remains reconciling: the fixed schema does not preserve enough history to prove absence of prior ambiguity after repeated claims. This conservative narrowing avoids a new history field. No malformed wire error, missing inventory or expired deadline supplies pre-entry evidence. Exhausted ambiguous attempts remain incomplete/reconciling with stable identities and persisted backoff.

Focused private tests establish valid claim/hash/resource completion first. Change owner, epoch, invocation, digest, resource and phase independently. Prove hashing follows reconstruction and unknown submission cannot release PendingStart. Exercise first-attempt definite denial against prior-ambiguity/later-attempt and transport-loss controls. Preserve registration and draining fields during late positive completion, and verify no ready transition. Check bounded delay at cap, attempts/failures/timestamp overflow, unchanged base on errors and retained-credit progress when new admission is full. Gate stale completion through PreparedProvision against takeover; use real Fake and settle gates before assertions. Caller-supplied facts are not a live authorization test.

## 4. C05d, one-round exact inventory recovery and retry planning

Depends on C05a/b/c. Own new `server/src/cluster/provision/reconcile.rs` and private `reconcile/tests.rs`; provision.rs changes only declaration/reexports. Do not create a controller loop, cache, provider abstraction, durable quarantine ledger or unbounded work queue.

Parent implementation clarification after C05c review: C05d additionally owns a narrow extraction of the existing claim construction and checked backoff helpers in `provision/delivery.rs`, with focused preservation checks in its private tests. The current builder permits only first attempts and its private StartClaim fields cannot be constructed by the reconciliation sibling. Keep first-attempt eligibility unchanged; the consumed inventory retry path may reach a separate closed reconciling branch that shares command reconstruction, delivery construction, arithmetic and complete candidate validation. Preserve the original captured root; do not reset a clone to pending, expose a raw StartClaim constructor, broaden fields or duplicate delivery construction. Shared helpers remain provision-private. Completion, confirmation and callback algorithms otherwise remain unchanged. This is an internal implementation boundary, not a new retry or authority rule.

`reconcile_start(root, owner, intent_id, inventory: InventoryEvidence, now_ms, proposal) -> Result<ReconcilePlan, StorageError>` consumes one complete inventory observation for one retained start. ReconcilePlan is `Change { candidate: ProvisionCandidate, classification: ReconcileClass }` or `Unchanged(ReconcileClass)`. ReconcileClass distinguishes recovered, absent, quarantined, terminal conflict, already known and needs termination reconciliation. Quarantine/contradiction produces a failure/backoff candidate; unchanged classifications grant no effect. Validate exact root association and current owner/epoch. A superseded observation requires a new round, never rebinding old evidence to a newer root. Unfinished in_progress claims after takeover first become reconciling while preserving their old delivery/attempts/backoff; no claim reset. Inventory failures have a separate fixed `inventory_failed_candidate` that persists sanitized scheduler degradation/backoff without treating partial/malformed data as a snapshot.

Only a unique positive nonterminated record with exact cluster/node/request may attach its resource to that retained launch and complete resource_known. Recover it even after resource/registration deadline expiry, including registered or unregistered draining nodes, without changing their phase, session, drain or verification. Never revive lost/stopped or failed terminal launches. Contradictory resources, unknown identities, duplicate/invalid inventories and evidence contradicting an irreversible witness fail closed and quarantine/degrade; attach or stop none of the implicated resources. Quarantine is a bounded classification plus persisted sanitized failure/backoff, not another durable record set. Complete inventory absence leaves capacity and first-stop credit intact.

`retry_start(root, owner, intent_id, inventory: InventoryEvidence, invocation_id, &AttachedConfig, now_ms, proposal) -> Result<StartClaim, StorageError>` is a distinct consumed one-round operation. It accepts only an unresolved reconciling launch, exact current inventory with no matching/unknown/conflicting resource, elapsed persisted backoff and attempts below max_attempts. It keeps node/launch/intent/template identity, builds fresh exact delivery bytes and uses mini 3's claim construction. This permits an explicit same-identity idempotent redelivery after reconciliation; it never sends HTTP itself. Inventory absence is not terminal evidence. At exhaustion return no new claim and preserve reconciling state for later positive inventory. Missing inventory, unverified caller booleans and stale root evidence permit no retry. One inventory observation is consumed once; the later runtime must retain this ownership through cancellation.

Positive terminated records are a distinct `NeedsTerminationReconciliation` classification carrying the exact retained binding, not resource_known success, stop authority or a stopped candidate. C06 must implement the irreversible terminal witness transition and any contradiction checks. A stop callback success/null is only accepted-command evidence; it cannot establish termination. Stop allocation/claim requires C06's durable authenticated exact-incarnation drain proof, never a caller bool. Late unregistered draining enrollment must precede that proof and stop allocation, as A16 requires; do not rewrite a retained stop's incarnation or relax state.rs.

Focused private tests recover the same late resource after unknown start/takeover and prove preserved launch, attempts, credit and draining registration. Use separate positive controls for exact resource, missing inventory, wrong request, unknown resource and collision. Reject structurally duplicate inventory in the codec before any usable observation. Show absence plus expired deadline yields no replacement; explicit same-ID retry obeys both backoffs and max_attempts. Reconstruct from an admin-changed/takeover root to prove persisted retry state survives while old inventory association fails. Test positive terminated classification separately from stop-null, absence and stale-heartbeat controls. At full admission budgets exact retained recovery still succeeds. Do not repeat the entire codec/CAS matrix.

## Later obligations, parent reconciliation and evidence limits

The next bounded handoff is Rust callback authorization and a one-attempt HTTP delivery owner on C05a's immutable bytes. It must freshly reconstruct/validate the received payload before digest comparison, read the durable in_progress delivery, and use `OwnershipGuard::authorize` with the captured generation, exact high-water root and fresh paired time immediately before replying to Python. Authorization and renewals must progress independently while callback I/O waits. Startup IPC, activation, retained async submissions/cancellation, periodic inventory and heartbeat loops, boot wiring and public-status encoding are separate assignments. No locks span storage/callback awaits; finite root parsing/cloning/encoding runs on the existing bounded coordinator CPU/I/O executor.

Parent must sequence C03b before C05b, serialize shared declarations and Rust/Cargo ownership after R03a3a, and require the real projected-status and fresh inventory gates before enabling allocation. C03c/d and authenticated probes remain later dependencies of freshness/routing/C06/C07, not implemented facts. C06 owns positive drainage and termination, C07 owns target changes/stabilization and failure replacement after exact resolution. E03/E04 must separately prove actual HTTP authorization during blocked callbacks, takeover, lost replies, provider idempotency, late registration/recovery and stop/termination behavior over real processes. Component Fake/codec tests cannot establish those properties.

No essential public protocol/schema decision is requested. The intentional limits are first-attempt-only terminal pre-entry failure and deferred positive termination transitions; richer repeated-attempt no-effect proofs would require a separate parent evidence design. Do not silently expand this slice to solve that history problem. Existing schema and retained identities suffice for the conservative foundation described here.
