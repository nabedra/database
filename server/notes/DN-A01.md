# DN-A01: Typed partition execution on network nodes

Design only, based on the current shared checkout. No Cargo commands or implementation changes. References below refer to this checkout, including its existing uncommitted partition work. The older plans are not the specification.

## Recommendation and decisions for the parent

Keep `serve(name, nodes=int|(min,max), start_node, stop_node, list_nodes)` and `Cluster(api_url, admin_token).scale/autoscale/status` as the management interface. The ORM retains its existing endpoint. A separate API tier routes whole operations to ready workers; every identical worker can coordinate operations and execute partition jobs for peers, including itself. Neither the dispatcher nor the worker entry point selects a cloud provider. Provisioning callbacks and storage adapters belong outside the execution contract.

Resolve these decisions before assigning implementation:

1. Use pure partition jobs with streamed results and coordinator-owned temporary files, as specified here. This preserves the current rule that no new table objects are uploaded until all candidates validate. Worker-side staging in shared storage is an alternative, but changes that rule, object-key ownership, cleanup, and `commit.rs`; do not mix the two approaches implicitly.
2. Preserve global mutation serialization across machines. A mutex per worker plus catalog compare-and-swap is insufficient to preserve the current admission/serialization behavior. Adopt a durable mutation owner with fencing and an operation journal before allowing multiple coordinators to publish. The journal and catalog publication must share an atomic authority, or place the fencing/idempotency state in the same conditional catalog update. A separate expiring lease checked before PUT cannot fence a delayed publisher.
3. Define a durable operation identity at the API tier. Recommend `(cluster_id, operation_id)` generated once at admission, with a request digest and retained terminal response. Existing `Request.request_id` is only response correlation today (`protocol.rs:316`); it is not already an idempotency guarantee. Repeated ORM calls remain distinct operations unless an explicit public retry contract is added.
4. Set independent operation/partition capacities and temporary-disk policy. Internal results cannot inherit the public 8 MiB limit. Rejecting a valid query because its unprojected intermediate exceeds 8 MiB changes current semantics.

Provisioning, heartbeat membership and controller takeover are parent-owned dependencies. This note defines their execution-facing requirements, not a second controller implementation.

## Version 1 job and result contract

Use authenticated internal HTTP over TCP with a separate worker credential, not the ORM/admin token. Production transport must authenticate the peer and protect credentials. JSON control records use explicitly tagged enums, strict fields, fixed-width integers and existing `Scalar`/`Key` representations. Float64 round trips must preserve finite values and signed zero. Reject unsupported versions and mismatched result tags before accepting data.

Each `JobEnvelope` contains `version=1`, `cluster_id`, `operation_id`, `job_id`, `attempt_id`, `request_digest`, `snapshot={catalog_revision, catalog_commit_id, catalog_etag}`, `ordinal:u32`, `table:TableDescriptor`, and `task`. The request digest binds all logical inputs; retries change only attempt/routing/deadline. `job_id` identifies the logical task, not the node. A configured storage namespace belongs to the worker's cluster binding, not to an arbitrary URL or credential supplied by a job. The descriptor, referenced file and task must agree on table identity.

`FileInput` is exactly `Legacy {object,row_count}` or `Partition {object,range,row_count,byte_size,payload_bytes}`. It carries the captured validated catalog facts. Empty-table preparation uses `None`. Continue parsing object keys against the table UUID and checking bytes, row counts, payload, key ordering and ranges through `load_file`. A worker never initializes or repairs the catalog as part of a job.

| Task tag and fields | Success payload |
| --- | --- |
| `get {file,key}` | `Get {source_rows:u64, source_payload_bytes:u64, row:Option<Row>}` |
| `collect {file,query:Query}` | `Collect {source_rows,source_payload_bytes,matched_rows:u64}` followed by full matching rows in current local order. Retain primary key, sort columns and all unprojected cells. |
| `count {file,query:Query}` | `Count {source_rows,source_payload_bytes,matched_rows:u64}`; count all matches without local limit. |
| `prepare {file:Option<FileInput>,range,mutation:RowMutation,target_bytes:u64}` | `Prepared {effect:MutationEffect,replacements:Option<Vec<PartMeta>>}` followed by closed Parquet bytes for each replacement. `None` means unchanged; `Some([])` means changed to empty. |

`RowMutation` permits only insert, insert_many, update, upsert and delete with the current payloads. `MutationEffect` is internally tagged `null | count {value:u64} | found {value:bool}`, unlike the public untagged mutation result. `PartMeta` contains range, row_count, payload_bytes, byte_size and a content digest; it has no final storage object name. The enclosing ordinal identifies the original partition; replacement order is the encoder's ascending range order. The coordinator assigns the current global upload ordinals after all preparation succeeds (`write.rs:212`).

Every result echoes version, cluster/operation/job/attempt IDs, request digest, snapshot identity and ordinal, and contains exactly one task-specific success or a sanitized `JobError {code,message}`. The dispatcher checks all of them, expected result kind, actual streamed lengths/digests and replacement metadata. Duplicate or late attempts cannot append a second result. Job errors have no database mutation outcome: the coordinator alone maps them to public `not_applied` before publication. A lost job reply is retryable because jobs perform reads/private computation only. Drain or account for all accepted attempts before disposing of their operation resources.

### Framing and limits

Use a length-prefixed JSON control header, at most 16 MiB, followed by length-prefixed data chunks of at most 64 KiB and an explicit terminal record. Bound every length before allocation and count bytes while receiving; do not trust Content-Length. Bound error messages to 1 KiB. The 16 MiB header accommodates an existing 8 MiB operation plus descriptor and captured metadata; each mutation payload is still bounded by its original 8 MiB request representation. Reject malformed/truncated streams as failed attempts, never partial success.

Collect rows are one streamed JSON array using existing row serialization. Its internal cap is `6 * MAX_DECODED_PAYLOAD_BYTES + 2` bytes, approximately 384 MiB, per operation across all partition results. This conservative bound follows from `snapshot.rs:53` payload accounting: strings escape by at most six bytes per source byte, numeric text fits within six times its accounted value bytes, and the per-cell/row accounting covers JSON punctuation and field names. Enforce the existing 100,000 source rows and 64 MiB source payload totals as well. Stream to bounded temporary storage or decode incrementally; do not allocate a 384 MiB network buffer. A single row may exceed 64 KiB, so chunks are byte fragments, not individual row messages. Get uses the same row bound, rather than an 8 MiB internal response bound.

Prepared data uses raw Parquet chunks, never base64. Each replacement is nonempty and at most 64 MiB, and Legacy input still allows 80 MiB (`snapshot.rs:35`). Preserve 128 columns, 10,000 batch/result rows, 100,000 table rows, 64 MiB logical payload, 1 MiB catalog and all footer guards. `target_bytes` validates through `PartitionSize` and is a soft target. A job produces at most 100,000 nonempty replacement files; across a batch the conservative pre-finalization bound is 110,000, since at most 10,000 rows enter an existing 100,000-row table. Bound metadata count and each encoded file accordingly. This intentionally does not add an 80 MiB aggregate encoded-output cap: many tiny partitions can exceed it under today's valid targets. Spool candidates incrementally on the coordinator, with explicit disk accounting; resource exhaustion fails before publication. No giant worst-case buffer is reserved.

After all job results succeed, the coordinator checks read source totals and invokes the existing global reducer once. Preserve primary-key tie breaks, one global limit, projection last, 10,000 result rows, bounded serialized result and the final 8 MiB HTTP envelope including request ID. Do not push projection/limit into version 1 jobs or declare success after a successful subset. Get still routes only its owning file; explain/describe/list do not download table objects.

For mutation, preserve original-index preparation error priority and whole-batch failure. Assemble changed/retained files, repair ranges, validate global row/payload totals and encode the bounded candidate catalog before uploading any table objects. Upload spooled replacements under the session's commit ID, then publish one conditional catalog update. No-op found=true remains distinct from changed=true, and a no-op needs no catalog revision. Temporary files are private, operation-owned and cleaned after completion; process restart may recompute them from the captured durable inputs.

## Minimal dispatcher and capacity invariant

Use one small `Dispatcher` enum with `Local(LocalDispatcher)` and `Remote(RemoteDispatcher)`. Its interface is `submit(JobEnvelope) -> JobHandle`, then `JobHandle.receive() -> JobResult` with streamed payload access. A closed enum avoids async trait-object machinery. Both invoke the same `run_job(envelope, storage, runtime)` handler and validate the same inputs/results. Local may retain the existing private generic `WorkerPool::submit` for thread scheduling, capturing only the owned typed envelope and worker execution context. Remote serializes that envelope; no user closure, plugin registry, Python callable, storage adapter or coordinator crosses the wire. Local data can use memory/spool handles but must pass the same logical bounds.

Expose `run_worker<B: ObjectStore>(storage, identity, membership, limits, listener, shutdown)` as the generic lifecycle entry point and `meshdb worker` as its executable adapter. Move `S3Store`/AWS imports out of `storage.rs` into an optional adapter module and feature; a worker using a different adapter must compile without AWS dependencies. Provider configuration stays in that adapter, outside job DTOs.

Define `O` running coordinating operations plus `Qo` bounded waiters per node, independently from `P` executing partition jobs plus `Qp` bounded waiters. Preserve `O>=1`, `P>=1`. An operation holds only its operation permit while awaiting jobs. A partition handler takes only partition capacity, runs to completion and never submits/awaits another partition job or acquires operation capacity. Coordinator validation/reduction runs under operation admission in a separate bounded CPU executor, never inside `WorkerPool` or a partition handler. Its scratch/spool accounting is included in the operation budget.

The remote partition route bypasses `Executor`'s operation semaphore. Otherwise `O=1` on a node coordinating its own operation deadlocks when its self-job waits for that same permit. The self path follows the same partition admission as peers. Do not hold a partition permit while waiting for its network destination to accept a job. Release a job's execution capacity when computation/output spooling finishes; network result delivery uses separately bounded I/O resources. Control/heartbeat/drain messages must remain runnable under both saturated budgets.

Replace `chunks(pool.worker_count())` with a fixed per-operation outstanding window `W`, backed by actual node partition admission. Never infer global capacity solely from a heartbeat. Busy nodes reject before acceptance; the dispatcher retries another ready node with a bounded deadline/backoff. Keep ordinal identity independent of placement, collect/drain the current window, choose its earliest ordinal error, and submit no later windows after failure. Memory is bounded by `O * W` results plus declared operation scratch, not cluster size. Saturating every operation slot still leaves `P` partition slots runnable on every node. This acyclic permit dependency is the concurrency argument; no timing assumptions are needed.

## Readiness, drain and durable recovery requirements

Ready means compatible protocol/codec version, authenticated listener, usable configured shared storage, initialized worker pool and valid node incarnation. Heartbeats expose incarnation, ready/draining state and separate operation/partition occupancy. Any ready worker can coordinate; dispatch uses immutable node incarnation to reject stale endpoints. Membership is advisory and never establishes whether a write committed.

Drain closes new whole-operation admission first and rejects new peer jobs before acceptance. Existing locally admitted operations retain permission to submit self jobs until they finish; peer rejections reroute, including back to that operation's coordinator. This avoids requiring every draining node to recognize operations admitted on other machines. Account for accepted inbound jobs before acknowledging shutdown. The controller may stop the process after both operation and partition counters reach zero, or recover its durable operations after a crash/forced stop. `runtime.rs:60` operation drain must finish before `WorkerThreads::shutdown`, and accepted work must survive client disconnects. Attempts have bounded leases/deadlines and temporary-output retention; a disconnected pure task may finish privately, but cannot publish or retain resources indefinitely.

The durable operation record needs input digest/body or immutable input reference, captured base catalog, commit ID, coordination generation, phase, candidate/response identity and terminal result. Read jobs and prepare jobs can be recomputed; catalog publication cannot be blindly replayed. During takeover, a fenced owner reconciles the durable publication record. Current `commit.rs` checks only the latest catalog's commit ID after an ambiguous PUT; a later commit can hide an earlier successful one. Retain durable commit evidence atomically with publication before promising safe operation retries across later writes. When that evidence is unavailable, retain public `outcome_unknown`; never report `not_applied` or replay the write. Persist no-op mutation outcomes too, since replay after another mutation may change the result. Provisioning-controller leadership and operation-mutation ownership are separate fences.
