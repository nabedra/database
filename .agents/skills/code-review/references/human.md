> Resource-aware scheduling of database queries and mutations across a worker cluster

- Verify that each worker handles multiple partitions and that a request respects its configured maximum number of workers, including during result reduction. See C04.
- Verify that each joining worker can advertise its own maximum thread count and resource limits. Enforce those limits across simultaneous requests, including on workers with different capacities. See C01-C03, M02.
- Submit multiple queries at once and add more while they run. Verify overlapping execution, correct results, fair progress, and redistribution of work when a worker becomes free. See C05-C07.
- Measure worker CPU utilization and memory use under sufficient load. Check for idle capacity despite eligible work, and record throughput, queue wait, completion latency, and memory peaks at increasing arrival rates. See B01-B02.
- Saturate the cluster and submit requests within admission limits. Track every accepted identity through the queue to a terminal outcome, with no missing or duplicate logical outcomes. Check explicit overload handling when queue count or byte limits are reached. See Q01-Q02.
- Verify that partition limits and task memory budgets bound actual working memory, including decoded data and intermediate results. Exercise large strings, wide rows, simultaneous memory-heavy jobs, and requests that cannot fit. See M01-M03.
- Fail one task while unrelated tasks are running. Verify that ordinary errors and contained thread panics leave other tasks and the executor usable, with resources released correctly. Exercise process failures separately before claiming stronger isolation. See F01-F03, R06.
- Submit unusual, malformed, and adversarial requests while the queue and workers are saturated. Verify typed errors, correct scheduling of valid work, and no leaked resource charges. Normal failures should use validation and typed error handling; assess their performance under load. See U02-U03, B02.
- Run equivalent query, mutation, saturation, and failure scenarios through local `serve` and separate API/workers. Verify the same admission, queue, scheduling, and recovery behavior. See U01.
- Verify that accepted requests survive API restarts and individual worker failures while at least one worker retains the complete request record. Include rolling restarts and queue transfer to joining workers. See Q03-Q04, R01-R03.
- Stop every worker with outstanding work, then restart. Verify that old outstanding requests are abandoned without automatic replay and that committed mutations remain durable. Reconcile uncertain commits before reporting their outcome. This supersedes the earlier disk-durable queue suggestion. See R04, T04-T05.
- Fail mutations during preparation, upload, and publication. Verify that all affected partitions become visible together or the previous committed state remains visible. Check concurrent mutations and lost commit responses without duplicate application. See T01-T06.
- Verify autoscaling only through a configured Kubernetes/AWS integration. Without an adapter, preserve fixed/manual cluster queue behavior; with one, test scale-up, safe drain, and provisioning failures without losing accepted work. See A01-A02.
