## Measure the existing cluster

Build the base commit and each candidate with the same optimized Rust profile and storage engine version. Run a separate production API with three registered Nabedra workers and persistent Docker volumes. Verify RF3, ready membership, and complete terminal outcomes. Keep the load driver within the aggregate four-CPU and 8,000,000,000-byte cap. Run the ScyllaDB RF3 and QUORUM reference on the same host and with the same per-node and driver limits, one database at a time. Record ScyllaDB commit-log sync configuration, client protocol, data layout and layer-specific acknowledgment conditions.

Use persistent client connections and seeded point updates against existing integer keys. Use a warm-up and three measured repetitions at each fixed arrival rate. Measure latency from scheduled arrival and report p50, p90, p95 and p99, acknowledged writes per second, overload, deadline failures, unresolved identities and final values. Capture driver timing and worker CPU, memory, I/O, network and available queue statistics. Compare the last stable common arrival rate and the highest rate each system can sustain with p99 under 10 ms. Sweep further if the highest point still meets that threshold. Record the benchmark commit, binary and image digests, CPU and memory limits, workload shape and run durations. ## Durable protocol changes

Enable new Raft commands only when every voter and learner that can receive or replay them supports their format. A service capability check establishes support at one endpoint. Compound applies need one bounded state batch that includes the applied log position. The existing batch reads use the pre-write snapshot, so pass intermediate state between steps explicitly. Check old checkpoints and partial manifests, retry with a changed digest, and inject failures before and after log sync, batch apply, and quorum acknowledgment. Keep synchronous durability and exercise O06, O07, O10, O11, O15, and O29.

A one-phase Data write requires the affected rows, local index updates, authoritative decision, and exact result to commit atomically in the same Data log. It also needs a durable request-to-shard binding for old receipts, split and restore lineage, and an owner fence checked by the same log entry. The current Timestamp protocol assigns the commit timestamp after durable preparation. An earlier reservation requires a read fence that prevents a successful cross-shard snapshot from passing the unresolved timestamp. Without that fence, the snapshot could miss a write that later becomes visible at or below its pinned timestamp. Prove snapshot visibility, Catalog lifecycle guards, and allocator failover before enabling this path. Exercise O07, O09–O11, O13–O16, and O29. ## Single-participant decision path

Measure the service-slot, notification, and replica-placement changes first. Then prototype a separate mode for a bounded point mutation with one Data participant. Keep the existing Status path for other transactions. Select the mode before preparing and record it durably for the attempt.

1. Keep the metadata-only Status UUID, digest, and original-run reservation before acceptance. Allocate and pin the original read timestamp, bind the exact accepted context, and complete the all-ready tentative, acceptance, and running copies at their existing barriers. Keep executable request bodies in RAM.
2. Install the immutable Status manifest and its decision home before Data prepares. Bind the locator to the cluster, database, request binding, attempt, manifest digest, Data group, and Timestamp group. Data checks its current fence, pinned snapshot, key versions, and Catalog guards, then durably prepares and seals private row and index changes.
3. Timestamp obtains a fresh authenticated Status read of the manifest, locator, and exact result, and a fresh authenticated Data quorum read of the matching seal. Run the two reads concurrently within the existing progress budget. One Timestamp entry checks the current fence and active bound pin, advances the same database timestamp watermark after durable prepare, and stores the immutable decision and exact result. The same Timestamp log orders aborts against commits for that home. Reconcile an ambiguous decision before advancing the attempt.
4. Data verifies the authoritative Timestamp decision and resolves idempotently. Status records the exact decision as evidence and copies the result into its receipt index in the existing resolution-recording entry. Until then, UUID retry, receipt lookup, and recovery follow the durable locator. An unavailable decision proof stays `outcome_unknown`. A cold restart honors decisions ordered before their fence and abandons remaining work after fencing. Replicate the exact terminal record to all ready workers before reporting success.

Compare the two-phase prototype with the same capped baseline. Seek one durable post-prepare decision proposal in place of Status `RecordPrepared`, Timestamp `AllocateCommit`, and Status `DecideCommit`. Measure actual quorum writes, nested RPCs, admission and queue time, successful p99, and goodput with full outcome accounting. Treat the remaining queue, Data resolution, and proof costs as measured limits on the gain.

For a deeper experiment, place the logical Status and Timestamp roles on one physical Raft log per database so reservation and pin, or prepared evidence and decision, can share a durable batch. Folding Data resolution into publication also requires the affected rows and local indexes on that log. Keep separate durable prepare and publish entries under O09. If Catalog remains separate, retain its guard proof and settlement. A per-shard watermark requires a fenced, durable closed cut and a real-time-consistent global snapshot token for cross-shard reads.
