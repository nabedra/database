Nabedra should route a primary-key operation directly to its owning data shard and do the least coordination its transaction, queue and receipt guarantees permit.

## Starting point and performance target

This proposal starts at `5a8ab42` on the OLTP performance branch. An earlier matched RF3 run measured a serial point-update median of 1,193.70 ms for Nabedra and 7.43 ms for ScyllaDB 6.2.3. Both acknowledged ten of ten writes and returned the correct rows. A later Nabedra-only comparison measured 1,794.35 ms for stock and 1,826.72 ms with confirmed terminal copies. Use the latter implementation as the correctness baseline and rerun ScyllaDB alongside it. The 42 service calls observed on each of two earlier traced writes include nested work. Their durations overlap. [Benchmark evidence](../docs/testing/evidence/oltp-latency/README.md)

## What to take from ScyllaDB

For an ordinary single-partition write in a stable topology, the coordinator sends the mutation to the replicas that own that partition. At RF3 and QUORUM, two acknowledgments suffice. Growing a cluster from 3 nodes to 30 leaves three destinations per write. One slow replica can catch up while other ranges continue to serve traffic. ScyllaDB's shard-aware routing directs work to the owning node and CPU. The acknowledgment is for the mutation. Nabedra's asynchronous API additionally exposes acceptance of a request that has yet to execute. [ScyllaDB write path](https://docs.scylladb.com/manual/stable/architecture/architecture-fault-tolerance.html) · [Consistency levels](https://docs.scylladb.com/manual/stable/cql/consistency.html) · [Shard and tablet routing](https://www.scylladb.com/2024/11/12/how-we-updated-scylladb-drivers-for-tablets-elasticity/)

Adopt partition-scoped fan-out, independent ownership, bounded per-shard scheduling and placement-aware routing behind the existing gateway. Keep ordered key ranges for ORM scans, Raft for replicated decisions, and `nabedra-kv` for MVCC. Make the queue a partitioned worker-memory service with its own RF3 placement. Co-locate its replicas with the data range for point operations where practical. Under stable placement, adding workers must add capacity for independent ranges without adding recipients or a global scheduler round trip to a point operation.

**Proposed performance target.** Aim for roughly equal speed. Use ±20% of ScyllaDB as the working equivalence band for each of client p50 latency, p99 latency and sustainable acknowledged operations/s. Measure latency at the same supported arrival rates and throughput at the same p99 budget. Publish paired confidence intervals. An interval inside the band establishes equivalence, one crossing its edge is inconclusive, and a result entirely beyond it is reported directionally. A favorable outlier needs no artificial slowdown. Include the existing 10 ms p99 budget where the reference sustains it. Count every scheduled arrival, require correct outcomes and zero rejects, drops or unresolved requests at qualifying rates, and report overload separately. Measure plain point reads and updates first, then compare conditional updates separately. The latter exercise ScyllaDB's lightweight transactions. [ScyllaDB conditional transactions](https://docs.scylladb.com/manual/stable/features/lwt.html)

## Public behavior and routing

Existing programs continue to use the installed ORM and wire format. For example, with a connected Python `db`:

```python
accounts = db.create_table("accounts", {"id": int, "active": bool}, key="id")
accounts.insert({"id": 42, "active": True})
assert accounts.update(42, {"active": False}) is True
assert accounts.get(42) == {"id": 42, "active": False}
assert accounts.update(99, {"active": True}) is False
```

Exercise all thirteen existing operations, types and errors through the public client. Preserve signed int64 and UTF-8 primary keys, exact bool and finite float rules, table UUIDs, duplicate-key conflicts, atomic batches, projection, counts, and deterministic ordering. Preserve the original request ID, body digest, authorization context, result and expiry through synchronous and asynchronous calls. Qualify each shipped SDK against the same wire fixtures. [ORM reference](../orm/python/docs/reference.md) · [OLTP contract O01–O04](../docs/testing/oltp-contract.md)

| Operation | Execution after admission |
| --- | --- |
| Primary-key get | Route by table UUID and key to one data shard. Read the row or its absence at the pinned snapshot. Resolve relevant intents before answering. |
| Point insert, update, upsert, delete | Start with update. Enable each other operation after its conflicts, no-ops, indexes and exact result pass. Qualify one data participant, shard-local index effects and valid catalog guards before selecting the decision protocol. |
| Batch | Derive every participant from the validated plan. Initially use the existing atomic protocol for every batch. Extend to a single-shard batch only after all-or-nothing and duplicate-key tests pass. |
| Range, secondary-index query, count | At one pinned snapshot, prune ranges using the current map, bound parallel shard reads, then apply global ordering, limit and count semantics. |
| Schema changes, splits, cross-shard transactions | Use the existing coordinator and durable distributed decision. Old, moved or already-prepared attempts always resolve through their recorded decision home. |

## Incremental implementation

1. **Measure the minimum cost of the current promises.** Extend the existing paired runners and request traces in the [benchmark suite](../docs/testing/evidence/oltp-latency/README.md). Correlate a sampled request's gateway arrival, last admission-copy ACK, dispatch, snapshot pin, route verification, data prepare, durable decision, visible apply, last terminal-copy ACK and HTTP return. Record sequential waits, overlap, quorum rounds, storage syncs, bytes and CPU throttling. Measure the ordinary untraced binary alongside it. Use fixture-only probes to time a full ready-set copy and a durable shard proposal independently. Compare the critical path with the ScyllaDB target before investing in another protocol. Run O23/O24 and Q03/Q06/B02.

2. **Route once and keep work on the owner.** In [worker runtime](../server/src/oltp_runtime/worker_runtime.rs), the [MVCC planner](../server/oltp-storage/src/oltp/mvcc/planner.rs) and [replica services](../server/oltp-replication/src/oltp_replication/service_rpc.rs), derive a bounded hint from cluster, database, table UUID, key range, group and generation. Let the scheduler prefer the owning worker when it has capacity. Dispatch the complete eligible operation there and reuse the placement lookup within the request. The receiver checks current authority, generation and fences before touching data. A stale hint triggers one bounded refresh inside the original deadline. After a possible mutation, reconcile by identity before any further attempt. Reuse authenticated sessions when measurement shows a benefit. Keep per-worker CPU/byte limits and protected progress capacity. Prototype per-core affinity only if profiles show contention or cross-core handoffs. Run O03/O05/O13/O16/O22 and C01–C07/M01–M03/F01–F03.

3. **Partition admission, scheduling and receipt delivery.** Implement the proposed protocol below across [admission](../server/src/oltp_runtime/admission.rs), [replica handling](../server/src/oltp_runtime/replica.rs) and the [remote API](../server/src/oltp_runtime/remote_api.rs). The existing all-ready path supplies the baseline and serves identities admitted under its contract. Roll out by database and protocol generation. Trace both paths through synchronous and asynchronous entry points.

4. **Remove repeated decisions from single-shard updates.** Reconcile the running branch's feature-gated Timestamp decision prototype with the new baseline first. Reuse qualified components and rerun integration tests against their exact combined revision. In [transaction execution](../server/src/oltp_runtime/transaction.rs), record the attempt's immutable decision home before Data prepares. Keep the existing snapshot pin and schema/conflict guards. After durable private prepare, validate the exact Status manifest and Data seal in parallel against current authority. One Timestamp Raft proposal then orders commit or abort, assigns the post-prepare commit timestamp on success and stores the result. Data resolves from this decision, Status materializes the receipt, and the terminal-copy rule recorded at admission completes before client success. Target one authoritative post-prepare decision proposal in place of separate prepared-status, timestamp allocation and status-decision steps. Count remaining resolution writes and quorum reads. Once a decision home is recorded, timeout or failure must reconcile there, including after owner replacement. Run O06–O11/O14–O16/O19/O29, Q03–Q06 and R03–R06. [Existing prototype design](oltp-latency.md#single-participant-decision-path)

5. **Decide whether to move the decision onto the data shard.** Use this second prototype only if step 4 still spends enough time in remote decisions to matter. Persist a stable UUID-to-shard binding before prepare so a retry with just the UUID can find its original decision after a split. Keep private prepare and publish ordered as separate durable entries. Prototype a shard-local publish entry that atomically applies the prepared base/index versions, immutable result, decision and applied log position. It must validate a post-prepare commit timestamp from the database ordering protocol and fence racing aborts and ownership changes. First keep the existing timestamp authority. Bind each allocated timestamp to the exact prepared attempt. A reader whose snapshot covers that timestamp must resolve the private intent through the recorded decision home or wait, including searches for absent rows and secondary-index entries. Recovery must settle a reserved timestamp before its fence permits reclamation. Moving timestamp allocation onto each shard needs a separate proof that every shard in a global snapshot has closed the chosen timestamp and no later commit can appear below it. Exercise a paused writer, later completed writer, multi-shard scan and allocator takeover in both orderings. Reject this variant if extra timestamp or receipt coordination cancels the saving, or the proof fails. Run O07–O11/O15/O16/O19/O29 before activation.

6. **Scale the paths that remain shared.** Spread independent range leaders across workers and disks, split hot ranges using measured bytes and load, and move bounded batches with learner catch-up and generation fencing. Measure a single hot key separately because a range split cannot distribute conflicting writes to that key. Compare throughput, per-worker CPU and recovery time under uniform, skewed and mixed reads/writes, including moves and compaction. Run fixed-total-resource tests first. Use the scale-out acceptance series below for the replicated capacity claim. Verify deployment isolation with two clusters using identical database names, keys and request UUIDs. Run O05/O16–O19/O21–O28, A01–A02 and B01–B02. Keep provider/AZ claims conditional on actual provider runs.

## Proposed OLTP queue contract

The current all-ready rule puts a complete copy on every ready worker. At W workers this costs at least W − 1 remote copies and makes an unrelated slow worker part of acceptance. The proposed RF3 queue changes the fault domain of **pending** work. The original [scheduling requirements](resource-aware-scheduling.md), [scheduler scenarios](../docs/testing/scheduler-contract.md) and [OLTP scenarios](../docs/testing/oltp-contract.md) remain the legacy acceptance oracle. Record the new scope in a versioned OLTP contract before activating it. OLAP continues to use its existing policy.

| Boundary | Proposed behavior |
| --- | --- |
| Identity and placement | Partition the request-identity index by cluster, database and UUID. Reuse the existing identity reservation to conditionally bind the digest, run, queue group, protocol version and decision home or locator. Two gateways submitting the same UUID for different keys converge here. Cache topology locally. For a point request choose queue placement alongside its target range. For a multi-shard request use the partitioned identity home as coordinator. Keep receipt-by-UUID discoverable after moves. |
| Accepted | The fenced queue owner sends the complete record to the three queue replicas in parallel. Before returning acceptance or starting execution, establish that a majority holds the exact executable body, accepted context, snapshot pin and version in RAM. First collect installation acknowledgments, then copy the acceptance marker and its evidence onto a majority that already holds the complete record. Count both rounds in benchmarks. Fuse them only if the recovery proof survives the same crash cuts. Prove takeover can distinguish an accepted record from partial installation, including loss of the first owner immediately after acknowledgment. Persist only identity, fencing and transaction metadata. Keep executable queue bodies in RAM. |
| Committed and observable | Data quorum commit and queue acceptance are distinct events. Report mutation success only after a durable authoritative decision, required visibility and quorum confirmation of the exact terminal record for that queue version. Carry the confirmation in the existing response when available. Reconcile a lost response through its UUID. An unavailable decision stays unknown. Catch up a lagging queue replica from surviving RAM and a lagging data voter through Raft log or snapshot. Bound both transfers and reserve capacity for foreground operations. |
| Ownership and memory | Give each queue group a fenced owner, monotonic term, bounded bytes and fair dispatch. An ownership change must recover complete records and reconcile prior acceptance/decision evidence before dispatch. Acknowledgments count distinct live incarnations in the same authorized placement. After a replica restarts without its RAM, require a verified state transfer before counting its votes for queue recovery. Old owners cannot dispatch or settle under the new term. A new run owner's fence adopts, under its term, the topology steps the lost owner had in flight (a replica move, a pending ready-set change), so a lost owner never blocks owner change or cold start (design review, `plans/oltp-engine.md`). Keep node-wide budget accounting local and compose shard budgets under the existing worker and request caps. |
| Failure and movement | One holder failure after RF3 quorum acceptance leaves a complete copy. If only one complete copy remains, retain it and defer execution until a safe authority and quorum can be established. During planned replacement or splits, fence the old generation, transfer the records, pins and receipt versions, verify a new quorum, then release old holders. Check lineage and old/new quorum evidence across the switch. A partition timeout alone never proves a body lost. |
| Last copy and cold start | If all complete RAM copies of an uncommitted request are lost, unrelated live workers cannot reconstruct it. Prove holder loss and fence outstanding attempts against their durable decision home before declaring abandonment. A prior commit always wins and recovers the exact result. If capabilities of the existing protocol cannot distinguish loss from partition, retain an unknown outcome until authoritative recovery. A full cluster stop abandons pending requests and preserves committed data. |

Run both legacy and scoped versions of Q03–Q06, R01–R06, O10/O14–O16/O23/O29 and Q06/T04. Pause the third queue replica while the first two are healthy, then pause an unrelated worker. With the relevant data and metadata quorums healthy, the scoped path must accept and return the correct committed result in both cases. Pause two before admission and assert that acceptance cannot be acknowledged. Lose the owner just after quorum installation, restart a voter with empty RAM, retry an identity against a different range, change membership mid-copy, isolate the last holder, and finally destroy all complete holders while unrelated workers stay live. Verify exact outcomes, retained pins, bounded memory and recovery after each cut. Add previously uncovered histories as named regressions. Keep the legacy last-copy and all-ready assertions on the legacy protocol.

## Scale-out acceptance

Run both engines at 3, 6 and 12 workers with RF3, equal per-node resources, equal data per node, comparable failure-domain placement and sufficient client capacity. Use separately provisioned capacity for this series. The four-CPU local suite measures contention and correctness. For uniform keys, report sustainable goodput per node and scaling efficiency, defined as throughput at N divided by throughput at 3 times 3/N, under the same p99 limit. Compare the efficiency curves with the same proposed ±20% band. Repeat with fixed data, skew, a single hot key and a live rebalance. Verify that healthy point writes target at most three queue replicas for the executable body and three data voters for the mutation as N grows. Record request-linked metadata fan-out and cross-core transfers too. Count distinct endpoints and bytes if the groups overlap. Instrument identity reservations, timestamp allocation, owner elections and gateway CPU separately. A serial cluster-wide service whose utilization saturates before the shards is an explicit redesign item: partition identity and admission by range/group, scale stateless gateways horizontally, and qualify timestamp batching or the closed-timestamp design in step 5 against O09 before changing ordering. Report recovery time, foreground p99 and data movement during replacement alongside healthy throughput.

## Recovery, rollout and release evidence

- Extend the current history oracle with old and new paths on the same keys. Inject deterministic failures before and after prepare, fsync, decision, apply, receipt copy and pin release. Include ambiguous storage errors, simultaneous UUID retries with conflicting bodies, cancellation, owner takeover, split during recovery, full-cluster stop and restore. Every surviving complete request retains its original identity and pin within the run. After all workers stop, fence undecided old attempts and abandon outstanding work. Recover committed data and its exact decision from durable state. Keep executable queue bodies in worker RAM. Run the named regressions in both contracts and retain new failing seeds. [Scheduler contract](../docs/testing/scheduler-contract.md) · [OLTP contract](../docs/testing/oltp-contract.md)
- Store queue policy and placement with each admitted identity. During rollout and rollback, drain old work using its original copy and acknowledgment rules. Keep old readers for existing manifests, logs, checkpoints and receipts. Deploy dual-format readers first. Enable new writes for one database only after every voter, learner and recovery/restore reader supports the format. Compare execution plans in read-only shadow mode, then canary new eligible attempts. Disable new routing on regression and drain or reconcile each in-flight attempt at its recorded home. A binary downgrade requires proven readability of every retained format or an explicitly verified backup/restore procedure. Exercise mixed-version restarts, old receipts, backup/PITR and changes to the ready set. Run O02/O10/O11/O14–O20/O29 and U01–U03.
- Run pinned release binaries sequentially on the same host, with three storage containers and an aggregate cap of four CPUs and 8 GB including clients and gateway. Match storage and per-node limits, data, replication factor, seed, arrivals, warm-up, TLS settings where supported and deadlines. Disclose protocol, isolation, sync and response-boundary differences. Compare current Nabedra, candidate, ScyllaDB plain QUORUM with batch commit-log sync, and a separate conditional workload. Use the planned synchronous PostgreSQL profile for transaction comparisons under O24. Verify row/index state, accepted IDs and original receipts after every phase.
- Keep the historical ten-write serial run for continuity. For a p99 claim, collect at least 10,000 successful operations per reported cell across at least three independent paired runs, publish sample counts and confidence intervals, and report insufficient samples explicitly. Sweep through saturation. Report offered and completed rates, rejection reasons, unresolved outcomes, scheduled-arrival p50/p95/p99, storage amplification, peak RSS, and time to recover service after loss of a worker. Keep each optimization only when it improves the target workload reproducibly and preserves the relevant correctness assertions. Run equivalent node-loss, network-partition, replacement and rejoin workloads on both systems. Report successful-operation rate during the fault, time to resume service, time to restore RF3 and post-recovery data verification. Compare each system against its declared acknowledgment contract. A partitioned Nabedra minority must fence writes. Record whether a delayed worker belongs to the affected queue or data quorum and whether unrelated shards continue to admit work. Publish these differences alongside healthy-node speed.

Each stage delivers a reversible change, a baseline/candidate comparison and an evidence record naming the executed scenario IDs. The first implementation milestone pairs a critical-path baseline with a scoped-queue prototype and the slow-third-replica fault test. Subsequent milestones qualify shard-local execution and reduce the remaining serial commit steps. End-to-end ScyllaDB parity and distributed failure behavior remain acceptance targets.
