Nabedra should route a primary-key operation directly to its owning data shard and do the least coordination its transaction, queue and receipt guarantees permit.

## Starting point and performance target

This proposal starts at `5a8ab42` on the OLTP performance branch. An earlier matched RF3 run measured a serial point-update median of 1,193.70 ms for Nabedra and 7.43 ms for ScyllaDB 6.2.3. Both acknowledged ten of ten writes and returned the correct rows. A later Nabedra-only comparison measured 1,794.35 ms for stock and 1,826.72 ms with confirmed terminal copies. Use the latter implementation as the correctness baseline and rerun ScyllaDB alongside it. The 42 service calls observed on each of two earlier traced writes include nested work. Their durations overlap. [Benchmark evidence](../docs/testing/evidence/oltp-latency/README.md)

Borrow ScyllaDB's placement-aware dispatch, bounded shard-local execution and parallel replication. Its ordinary RF3 QUORUM write can finish after two replicas acknowledge. Nabedra also promises a recoverable request identity, atomic ORM operations, consistent snapshots, and queue copies on every ready worker. Keep the existing range partitioning, RocksDB MVCC storage, and Raft groups for this refactor. Ordered key ranges serve the ORM's range queries. ScyllaDB's tablet-aware routing principle works with that layout. [ScyllaDB routing design](https://www.scylladb.com/2024/11/12/how-we-updated-scylladb-drivers-for-tablets-elasticity/) · [Consistency levels](https://docs.scylladb.com/manual/stable/cql/consistency.html) · [Nabedra scheduling requirements](resource-aware-scheduling.md)

**Proposed parity criterion.** At the same offered rate, resources and RF3, target Nabedra/ScyllaDB ratios at or below 1.0 for client p50 and p99, and at or above 1.0 for sustainable acknowledged writes/s at p99 under 10 ms. Count all scheduled arrivals. A qualifying rate requires all offered operations to finish correctly within deadline, with zero drops, rejections or unresolved identities. Report overload separately. Claim an improvement only when paired repetitions resolve the difference beyond run variability. Report results per workload. Start with plain primary-key reads and updates. A ScyllaDB conditional update is an additional reference for conditional semantics. Neither ScyllaDB reference exercises the Nabedra receipt contract. [ScyllaDB conditional transactions](https://docs.scylladb.com/manual/stable/features/lwt.html)

## Public behavior and routing

Existing programs continue to use the installed ORM and wire format. For example, with a connected Python `db`:

```python
accounts = db.create_table("accounts", {"id": int, "active": bool}, key="id")
accounts.insert({"id": 42, "active": True})
assert accounts.update(42, {"active": False}) is True
assert accounts.get(42) == {"id": 42, "active": False}
assert accounts.update(99, {"active": True}) is False
```

Exercise all thirteen existing operations, types and errors through the public client. Preserve signed int64 and UTF-8 primary keys, exact bool and finite float rules, table UUIDs, duplicate-key conflicts, atomic batches, projection, counts, and deterministic ordering. Preserve the original request ID, body digest, authorization context, result and expiry through synchronous and asynchronous calls. Qualify each shipped SDK against the same wire fixtures. [ORM reference](../orm/python/docs/reference.md) · [OLTP contract O01–O04](../docs/testing/oltp-contract.md)

| Operation | Execution after admission |
| --- | --- |
| Primary-key get | Route by table UUID and key to one data shard. Read the row or its absence at the pinned snapshot. Resolve relevant intents before answering. |
| Point insert, update, upsert, delete | Start with update. Enable each other operation after its conflicts, no-ops, indexes and exact result pass. Qualify one data participant, shard-local index effects and valid catalog guards before selecting the decision protocol. |
| Batch | Derive every participant from the validated plan. Initially use the existing atomic protocol for every batch. Extend to a single-shard batch only after all-or-nothing and duplicate-key tests pass. |
| Range, secondary-index query, count | At one pinned snapshot, prune ranges using the current map, bound parallel shard reads, then apply global ordering, limit and count semantics. |
| Schema changes, splits, cross-shard transactions | Use the existing coordinator and durable distributed decision. Old, moved or already-prepared attempts always resolve through their recorded decision home. |

## Incremental implementation

1. **Measure the minimum cost of the current promises.** Extend the existing paired runners and request traces in the [benchmark suite](../docs/testing/evidence/oltp-latency/README.md). Correlate a sampled request's gateway arrival, last admission-copy ACK, dispatch, snapshot pin, route verification, data prepare, durable decision, visible apply, last terminal-copy ACK and HTTP return. Record sequential waits, overlap, quorum rounds, storage syncs, bytes and CPU throttling. Measure the ordinary untraced binary alongside it. Use fixture-only probes to time a full ready-set copy and a durable shard proposal independently. Compare the critical path with the ScyllaDB target before investing in another protocol. Run O23/O24 and Q03/Q06/B02.

2. **Route once and keep work on the owner.** In [worker runtime](../server/src/oltp_runtime/worker_runtime.rs), the [MVCC planner](../server/src/oltp/mvcc/planner.rs) and [replica services](../server/src/oltp_replication/service_rpc.rs), derive a bounded hint from cluster, database, table UUID, key range, group and generation. Let the scheduler prefer the owning worker when it has capacity. Dispatch the complete eligible operation there and reuse the placement lookup within the request. The receiver checks current authority, generation and fences before touching data. A stale hint triggers one bounded refresh inside the original deadline. After a possible mutation, reconcile by identity before any further attempt. Reuse authenticated sessions when measurement shows a benefit. Keep per-worker CPU/byte limits and protected progress capacity. Prototype per-core affinity only if profiles show contention or cross-core handoffs. Run O03/O05/O13/O16/O22 and C01–C07/M01–M03/F01–F03.

3. **Shorten queue and receipt delivery.** In [admission](../server/src/oltp_runtime/admission.rs), [replica handling](../server/src/oltp_runtime/replica.rs) and the [remote API](../server/src/oltp_runtime/remote_api.rs), measure each required copy/version transition. Fan out independent copies concurrently within the existing byte and peer limits. Piggyback acknowledgments and completion evidence on existing replies where the receiver can verify the exact run, ready-set revision, worker incarnation, request digest and version. Preserve every required transition and revalidate membership before exposing acceptance or success. Reuse the retained confirmed-copy fix. Bound waiters, deadlines and backpressure. Previous notification and placement candidates regressed, so repeat them only against a newly identified wait. Run Q01–Q06, R01–R06, C07/M02, Q06/T04 and O10/O14/O15/O23 on the gateway and direct worker API.

4. **Remove repeated decisions from single-shard updates.** Reconcile the running branch's feature-gated Timestamp decision prototype with the new baseline first. Reuse qualified components and rerun integration tests against their exact combined revision. In [transaction execution](../server/src/oltp_runtime/transaction.rs), record the attempt's immutable decision home before Data prepares. Keep the existing snapshot pin and schema/conflict guards. After durable private prepare, validate the exact Status manifest and Data seal in parallel against current authority. One Timestamp Raft proposal then orders commit or abort, assigns the post-prepare commit timestamp on success and stores the result. Data resolves from this decision, Status materializes the receipt, and all-ready terminal confirmation completes before client success. Target one authoritative post-prepare decision proposal in place of separate prepared-status, timestamp allocation and status-decision steps. Count remaining resolution writes and quorum reads. Once a decision home is recorded, timeout or failure must reconcile there, including after owner replacement. Run O06–O11/O14–O16/O19/O29, Q03–Q06 and R03–R06. [Existing prototype design](oltp-latency.md#single-participant-decision-path)

5. **Decide whether to move the decision onto the data shard.** Use this second prototype only if step 4 still spends enough time in remote decisions to matter. Persist a stable UUID-to-shard binding before prepare so a retry with just the UUID can find its original decision after a split. Keep private prepare and publish ordered as separate durable entries. Prototype a shard-local publish entry that atomically applies the prepared base/index versions, immutable result, decision and applied log position. It must validate a post-prepare commit timestamp from the database ordering protocol and fence racing aborts and ownership changes. First keep the existing timestamp authority. Bind each allocated timestamp to the exact prepared attempt. A reader whose snapshot covers that timestamp must resolve the private intent through the recorded decision home or wait, including searches for absent rows and secondary-index entries. Recovery must settle a reserved timestamp before its fence permits reclamation. Moving timestamp allocation onto each shard needs a separate proof that every shard in a global snapshot has closed the chosen timestamp and no later commit can appear below it. Exercise a paused writer, later completed writer, multi-shard scan and allocator takeover in both orderings. Reject this variant if extra timestamp or receipt coordination cancels the saving, or the proof fails. Run O07–O11/O15/O16/O19/O29 before activation.

6. **Scale the paths that remain shared.** Spread independent range leaders across workers and disks, split hot ranges using measured bytes and load, and move bounded batches with learner catch-up and generation fencing. Measure a single hot key separately because a range split cannot distribute conflicting writes to that key. Compare throughput, per-worker CPU and recovery time under uniform, skewed and mixed reads/writes, including moves and compaction. Run fixed-total-resource tests first. Test horizontal capacity on separately provisioned hardware with equal resources per node when available. Verify deployment isolation with two clusters using identical database names, keys and request UUIDs. Run O05/O16–O19/O21–O28, A01–A02 and B01–B02. Keep provider/AZ claims conditional on actual provider runs.

**Scaling limit to surface early.** With W ready workers, the current admission rule sends at least W − 1 additional complete request copies for a request originating on a worker. Parallelism can shorten the wait, but total bytes grow with W and the slowest required copy can delay success. Benchmark a slow ready follower and increasing ready membership at fixed RF3. If this limit dominates, publish the measured bandwidth and latency cost. A shard-scoped RAM queue would change which surviving workers can recover accepted work. That would require a separate product decision and revised Q03/O14/O23 guarantees. It is outside this refactor.

## Recovery, rollout and release evidence

- Extend the current history oracle with old and new paths on the same keys. Inject deterministic failures before and after prepare, fsync, decision, apply, receipt copy and pin release. Include ambiguous storage errors, simultaneous UUID retries with conflicting bodies, cancellation, owner takeover, split during recovery, full-cluster stop and restore. Every surviving complete request retains its original identity and pin within the run. After all workers stop, fence undecided old attempts and abandon outstanding work. Recover committed data and its exact decision from durable state. Keep executable queue bodies in worker RAM. Run the named regressions in both contracts and retain new failing seeds. [Scheduler contract](../docs/testing/scheduler-contract.md) · [OLTP contract](../docs/testing/oltp-contract.md)
- Keep old readers for existing manifests, logs, checkpoints and receipts. Deploy dual-format readers first. Enable new writes for one database only after every voter, learner and recovery/restore reader supports the format. Compare execution plans in read-only shadow mode, then canary new eligible attempts. Disable new routing on regression and drain or reconcile each in-flight attempt at its recorded home. A binary downgrade requires proven readability of every retained format or an explicitly verified backup/restore procedure. Exercise mixed-version restarts, old receipts, backup/PITR and changes to the ready set. Run O02/O10/O11/O14–O20/O29 and U01–U03.
- Run pinned release binaries sequentially on the same host, with three storage containers and an aggregate cap of four CPUs and 8 GB including clients and gateway. Match storage and per-node limits, data, replication factor, seed, arrivals, warm-up, TLS settings where supported and deadlines. Disclose protocol, isolation, sync and response-boundary differences. Compare current Nabedra, candidate, ScyllaDB plain QUORUM with batch commit-log sync, and a separate conditional workload. Use the planned synchronous PostgreSQL profile for transaction comparisons under O24. Verify row/index state, accepted IDs and original receipts after every phase.
- Keep the historical ten-write serial run for continuity. For a p99 claim, collect at least 10,000 successful operations per reported cell across at least three independent paired runs, publish sample counts and confidence intervals, and report insufficient samples explicitly. Sweep through saturation. Report offered and completed rates, rejection reasons, unresolved outcomes, scheduled-arrival p50/p95/p99, storage amplification, peak RSS, and time to recover service after loss of a worker. Keep each optimization only when it improves the target workload reproducibly and preserves the relevant correctness assertions. Run equivalent node-loss, network-partition, replacement and rejoin workloads on both systems. Report successful-operation rate during the fault, time to resume service, time to restore RF3 and post-recovery data verification. Compare each system against its declared acknowledgment contract. A partitioned Nabedra minority must fence writes. A delayed ready worker can stall admission until a safe membership transition. Publish these differences alongside healthy-node speed.

Each stage delivers a reversible change, a baseline/candidate comparison and an evidence record naming the executed scenario IDs. The first implementation milestone is a time breakdown and a measured choice between reducing queue waits, remote transaction decisions, and redundant routing. End-to-end ScyllaDB parity and distributed failure behavior remain acceptance targets.
